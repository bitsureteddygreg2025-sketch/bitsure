1. RÉSUMÉ DE L'ARCHITECTURE
Le projet est un bot Telegram de trading nommé Bitsure Teddy. Le point d’entrée est main.py, qui initialise la base PostgreSQL, importe les handlers utilisateur/admin/trading, démarre plusieurs tâches périodiques, enregistre les commandes Telegram, puis lance le bot en webhook ou polling selon WEBHOOK_URL. 

État du repository pendant l’audit : aucune modification non commitée détectée.

Commandes d’audit utilisées :

✅ git status --short && git log --oneline -5 && rg --files -g '!__pycache__' -g '!*.pyc' | sort

✅ python -m py_compile main.py bot_handlers.py trading_handlers.py execution_engine.py signal_engine.py history_manager.py admin_handlers.py database.py trading_config.py position_manager.py risk_manager.py binance_manager.py paper_trader.py user_manager.py alert_manager.py data_fetcher.py indicators.py payments.py utils.py market_hours.py trading_logger.py

✅ python - <<'PY' ... ast/re/find callbacks and commands ... PY

✅ git show --stat --oneline HEAD && git show HEAD^:main.py ... && git show HEAD^:history_manager.py ...

Modules principaux

Démarrage bot	main.py	Initialise DB, services, commandes, callbacks, schedulers, polling/webhook. 
Handlers utilisateur	bot_handlers.py	/start, /help, /menu, analyse, prix, alertes, watchlist, paramètres, historique, paper trading, paiements, schedulers signaux/rapports. 
Handlers AutoTrade	trading_handlers.py	Config Binance, mode spot/futures, analyse périodique, positions, confirmation/rejet signaux. 
Exécution trading	execution_engine.py	Lit les signaux pending/active, filtre risque/config, ouvre position ou demande confirmation, analyse périodique Binance.

Risque	risk_manager.py	Limites positions, whitelist/blacklist, cooldown, pertes journalières, sizing. 
Positions réelles	position_manager.py	Lit/ferme les trades, surveille SL/TP/trailing stop, emergency stop. 
Signaux	signal_engine.py	Analyse technique, styles, scoring, WAIT/BUY/SELL, SL/TP, RR. 
Historique signaux	history_manager.py	Insertion et lecture des signaux PostgreSQL, exclusion des WAIT à l’insertion et lecture. 
Base PostgreSQL	database.py	Crée users, usage, settings, watchlist, alerts, signals, paper_positions, paper_capitals, trading_config, binance_credentials, trades. 
Utilisateurs	user_manager.py	Accès, rôles, limites, watchlist, settings, paiements Binance, approbation admin. 
Alertes	alert_manager.py	CRUD alertes et monitoring prix toutes les 60s. 
Paper trading	paper_trader.py	Simulateur long/short, levier, frais, slippage, capital, SL/TP, historique. 
Admin	admin_handlers.py	Stats, approbation, broadcast, switch API, DB query, export, clean WAIT, clear history. 
Flux global
main.py importe config.py, qui exige TELEGRAM_TOKEN et ADMIN_ID au chargement. Sans ces variables, le processus échoue avant lancement. 

get_db() est appelé au démarrage et crée/altère le schéma PostgreSQL. 

Les commandes sont enregistrées dans handlers, puis passées à CommandHandler. Toutes les commandes restent techniquement enregistrées, même si elles ne sont plus toutes visibles dans le menu Telegram natif. 

Les callbacks inline sont routés par 5 CallbackQueryHandler : menu général, sélection symbole, paiement plan, trading, conditions d’utilisation. 

Les schedulers démarrés : rapport hebdomadaire, surveillance signaux/paper, alertes, AutoTrade périodique et monitoring positions.

Points importants :

analyse() utilise le timeframe et style utilisateur stockés dans settings, appelle SignalEngine.analyze(), génère un graphique, puis appelle HistoryManager.add_signal(). 

WAIT n’est pas persisté par add_signal(), donc l’utilisateur reçoit quand même l’analyse mais sans ID. 

Il existe trois blocs identiques de vérification du nombre de signaux pending dans analyse(), ce qui est une duplication évidente.

Problème précis : paperdir_ construit context.args = [parts[2].lower(), parts[1]]. Pour paperdir_BTCUSD_BUY, cela devient ["buy", "BTCUSD"], ce qui correspond bien à l’API paper().  Mais symbol_callback() crée les boutons avec paperdir_{symbol}_BUY / paperdir_{symbol}_SELL.  Ensuite paper() ne reconnaît pas sell comme ouverture short ; sell est une fermeture de longs, alors que l’ouverture short attend short.  Donc le bouton SELL 🔴 ne crée pas une position short : il tente de fermer une position BUY existante. C’est incohérent avec le libellé “BUY / SELL”.

Incohérence importante : send_settings_menu() est décorée par @check_limit, alors que ce n’est pas un handler Telegram autonome mais une fonction utilitaire appelée avec des paramètres non standard (lang, tf, style, etc.).  Cela semble dangereux : le décorateur check_limit attend un Update en premier argument et fait update.effective_user.id.  Si le décorateur est réellement appliqué à send_settings_menu, les appels comme send_settings_menu(lang, tf, style, uid, ...) devraient provoquer une erreur car lang est une chaîne, pas un Update. Pourtant ce code est appelé depuis menu_parametres, settings, etc.

7. FONCTIONNALITÉS CASSÉES
7.1 Menu Paramètres probablement cassé par décorateur incorrect
send_settings_menu() est décorée par @check_limit, mais elle n’a pas une signature de handler Telegram ; elle prend lang, tf, style, uid, send_fn.  Le décorateur check_limit attend que le premier argument soit un objet Update et lit update.effective_user.id.  Les appels actuels passent une string comme premier argument. 

Impact probable : /settings, bouton menu_parametres, retours après choix timeframe/style/langue peuvent lever AttributeError: 'str' object has no attribute 'effective_user'.

Confiance : élevée.

7.2 Bouton Paper SELL incohérent
Le bouton SELL 🔴 génère paperdir_{symbol}_SELL.  Le routeur convertit cela en context.args = ["sell", symbol].  Or paper() documente short pour ouvrir un short, tandis que sell ferme toutes les positions BUY du symbole. 

Impact : depuis le menu, l’utilisateur qui clique SELL n’ouvre pas de short ; il tente une fermeture.

Confiance : élevée.

7.3 Bouton “Modifier SL/TP” cassé
Le prompt semi-automatique ajoute trading_edit_<id>.  Le callback répond à l’utilisateur d’utiliser /editsignal <id> <nouveau_sl> <nouveau_tp>.  Aucune commande /editsignal n’est enregistrée dans main.py. 

Impact : fonctionnalité annoncée mais inutilisable.

Confiance : élevée.

7.4 Monitoring paper dans position_manager cassé / doublonné
position_manager.monitor_open_positions() tente from paper_trader import paper_trader.  Or paper_trader.py définit la classe PaperTrader, mais ne définit pas de singleton module paper_trader en fin de fichier.  Le singleton existe dans bot_handlers.py sous forme locale paper_trader = PaperTrader(). 

Impact : le bloc paper de monitor_open_positions() échoue et loggue une erreur à chaque passage. Il existe déjà une autre surveillance paper dans bot_handlers.check_paper_exits(), donc il y a aussi duplication de responsabilité. 

Confiance : élevée.

7.5 settings_timeframe absent en anglais
Les clés anglaises autour de settings contiennent settings_style, settings_lang, settings_edit, mais pas settings_timeframe dans la zone anglaise détectée.  send_settings_menu() appelle get_text(lang, 'settings_timeframe').  get_text() renvoie la clé brute si absente. 

Impact : en anglais, le menu peut afficher settings_timeframe : 1h.

Confiance : moyen à élevé.

7.6 /autotrade n’ouvre pas le menu AutoTrade
La commande /autotrade fait uniquement un toggle ON/OFF après vérification des clés.  Pourtant le menu Telegram visible la décrit comme “Menu AutoTrade Binance”. 

Impact : incohérence UX ; l’utilisateur peut activer/désactiver sans voir/configurer le module.

Confiance : élevé.

7.7 Paiement Telegram Stars probablement non fonctionnel
send_invoice() appelle reply_invoice(... provider_token="", currency="XTR", ...).  Selon le contexte Telegram Stars, cela peut être volontaire pour XTR, mais le code ne documente pas l’intention ni ne gère d’erreur. À auditer en environnement réel.

Confiance : moyen.

11. ERREURS ET INCOHÉRENCES
Incohérences menus / callbacks
send_settings_menu() décorée à tort : c’est le problème le plus critique car il peut casser /settings et le bouton Paramètres. 

Paper SELL vs short : le menu promet achat/vente mais la commande interne sell ferme au lieu d’ouvrir short. 

Bouton edit SL/TP sans commande associée. 

Callbacks orphelins dans regex : check_subscription, clearhistory_. 

Incohérences commandes / visibilité
Beaucoup de commandes sont enregistrées mais retirées du menu natif Telegram. 

/autotrade est visible comme “Menu AutoTrade Binance”, mais ne montre pas le menu. 

Incohérences trading
Mode spot/futures : le choix est persisté en DB, pas temporaire de session. Cela peut être acceptable selon logique projet, mais ne correspond pas strictement au mot “temporairement”. 

Analyse périodique : elle scanne tous les symboles tradables via get_tradable_symbols(), puis applique whitelist/blacklist.  C’est fonctionnel mais très coûteux si beaucoup d’utilisateurs sont activés.

Spot + SELL : open_position() rejette les shorts spot.  C’est logique, mais les signaux SELL en spot peuvent devenir des erreurs d’exécution si non filtrés avant tentative.

Incohérences base de données
Le schéma signals inclut direction, status, validation_status, etc.  HistoryManager.add_signal() ignore WAIT, puis stocke BUY/SELL avec pending si validé. 

Les champs DCA/trailing existent en DB/config mais sont peu ou pas branchés dans l’interface. 

Erreurs silencieuses
safe_edit() finit par except Exception: pass, donc certains échecs d’édition/envoi disparaissent sans log. 

UserManager.add_to_watchlist() ignore silencieusement les exceptions d’insert. 

position_manager.monitor_open_positions() ignore silencieusement certaines erreurs d’envoi paper et loggue seulement globalement l’import impossible probable de paper_trader. 

process_signal_for_user() ignore silencieusement un signal sous min_score sans le marquer skipped, donc il peut être repris indéfiniment par fetch_pending_signals().
